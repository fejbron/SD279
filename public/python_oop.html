Introduction

Why OOP in a Data Structures Course?

An Abstract Data Type says what a structure does. A class is how we build it in code.

  • Every structure this semester — stack, queue, linked list, hash map, tree, heap, graph — will be written as a class
  • Its methods are the ADT operations: push, pop, insert, search…
  • Its attributes hold the hidden representation: a list, a head pointer, a root node
  • Users depend on the interface, so we can swap the implementation later
ADT ideaPython OOP tool
Interface (operations)Public methods
Hidden representationAttributes (by convention _name)
Several implementationsSubclasses of an abstract base class
Linked structuresObjects holding references to other objects
"Empty" errorsRaising exceptions

Classes & Objects

Classes and Objects

class Student: def __init__(self, name, index_no): self.name = name # attributes self.index_no = index_no def greet(self): # method return f"Hi, I am {self.name}" a = Student("Ama", "CE/22/001") b = Student("Kofi", "CE/22/002") print(a.greet()) # Hi, I am Ama print(b.name) # Kofi
  • A class is a blueprint; an object (instance) is one thing built from it
  • Calling Student(...) creates a new object and runs __init__ on it
  • Each object keeps its own attribute values — a.name and b.name differ
  • Methods are functions defined inside the class that act on one object
Naming

Classes use CapWords (LinkedList); methods and attributes use snake_case (push_front).

Classes & Objects

self and __init__

self is the object the method was called on. Python passes it in for you.

a.greet() # is exactly the same as Student.greet(a)
  • __init__ is the initialiser: it sets up attributes on a brand-new object
  • Always the first parameter of an instance method: def push(self, x)
  • Forgetting self. creates a local variable that vanishes when the method returns
Common bug

def __init__(self, data): data = data — this assigns to a local variable. It must be self.data = data.

Who calls __init__?

Node(5) → Python creates an empty object, then calls Node.__init__(obj, 5), then returns obj.

Return value

__init__ must return None. It initialises; it does not create.

Classes & Objects

Instance vs Class Attributes

class Bag: items = [] # CLASS attribute: one list shared by every Bag def add(self, x): self.items.append(x) b1, b2 = Bag(), Bag() b1.add(1) print(b2.items) # [1] <- b2 sees b1's item! class SafeBag: def __init__(self): self.items = [] # INSTANCE attribute: one list per bag

Mutable data (lists, dicts) belongs in __init__, never at class level.

  • Instance attributes live on each object: self.items = []
  • Class attributes live on the class and are shared — fine for constants like DEFAULT_CAPACITY = 16
  • Same trap with default arguments: def __init__(self, items=[]) shares one list across calls — use items=None

Encapsulation

Encapsulation and @property

class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self._balance = balance # "internal" by convention @property def balance(self): # read it like an attribute return self._balance def deposit(self, amount): if amount <= 0: raise ValueError("deposit must be positive") self._balance += amount acct = BankAccount("Ama") acct.deposit(50) print(acct.balance) # 50 # acct.balance = 999 -> AttributeError (no setter)
  • Hide the representation; expose only safe operations
  • _name — "internal, please don't touch" (a convention)
  • __name — name-mangled to _Class__name to avoid clashes in subclasses
  • @property gives read access without allowing writes, and lets you add validation later without changing callers

A stack that exposes its list lets users insert in the middle and break LIFO. Encapsulation protects the invariant.

Dunder Methods

Example: a Stack That Feels Built-in

class Stack: def __init__(self): self._items = [] def push(self, x): self._items.append(x) def pop(self): if not self._items: raise IndexError("pop from empty stack") return self._items.pop() def peek(self): if not self._items: raise IndexError("peek at empty stack") return self._items[-1] def __len__(self): return len(self._items) def __repr__(self): return f"Stack({self._items})" s = Stack() s.push(1) s.push(2) print(len(s), s.peek(), s) # 2 2 Stack([1, 2])
  • The list is hidden behind _items — only push / pop / peek touch it
  • len(s) works because of __len__; if s: also works (empty → falsy)
  • Errors are explicit: an empty pop raises IndexError with a clear message

Dunder Methods

Iteration with __iter__ and yield

class Node: def __init__(self, data, next=None): self.data = data self.next = next class LinkedList: def __init__(self): self.head = None def push_front(self, x): self.head = Node(x, self.head) def __iter__(self): # makes "for x in ll" work cur = self.head while cur: yield cur.data cur = cur.next def __contains__(self, x): # makes "x in ll" work return any(v == x for v in self) ll = LinkedList() for v in (3, 2, 1): ll.push_front(v) print(list(ll), 2 in ll) # [1, 2, 3] True
  • A function containing yield is a generator: it pauses at each yield and resumes on the next request
  • __iter__ returning a generator is the simplest way to make any structure iterable
  • Once iterable, list(), sum(), any() and for all work for free

You will use exactly this pattern for linked lists (week 6) and tree traversals (week 8).

Inheritance

Inheritance and super()

class Animal: def __init__(self, name): self.name = name def speak(self): return "..." def intro(self): return f"{self.name} says {self.speak()}" class Dog(Animal): def speak(self): # override return "Woof" class Puppy(Dog): def __init__(self, name, age): super().__init__(name) # reuse the parent's setup self.age = age p = Puppy("Bingo", 1) print(p.intro()) # Bingo says Woof print(isinstance(p, Animal)) # True
  • A subclass inherits every attribute and method of its parent
  • It can override a method by defining one with the same name
  • super().__init__(...) runs the parent's initialiser — forget it and self.name never exists
  • Lookup order (MRO): Puppy → Dog → Animal → object

intro() lives in Animal but calls self.speak() — the subclass version runs. That is polymorphism.

Polymorphism

Polymorphism and Duck Typing

class Queue: def __init__(self): self._items = [] def add(self, x): self._items.append(x) def remove(self): return self._items.pop(0) class Stack: def __init__(self): self._items = [] def add(self, x): self._items.append(x) def remove(self): return self._items.pop() def drain(container, values): for v in values: container.add(v) return [container.remove() for _ in values] print(drain(Queue(), [1, 2, 3])) # [1, 2, 3] (FIFO) print(drain(Stack(), [1, 2, 3])) # [3, 2, 1] (LIFO)

"If it walks like a duck and quacks like a duck…" — drain only needs add and remove; it never checks the type.

  • Same call, different behaviour depending on the object
  • This is how one BFS function can work with any queue implementation
  • Note: list.pop(0) is O(n) — week 5 replaces it with collections.deque

Abstraction

Abstract Base Classes = ADTs in Code

from abc import ABC, abstractmethod class Container(ABC): @abstractmethod def add(self, x): ... @abstractmethod def remove(self): ... def is_empty(self): # shared, concrete method return len(self) == 0 class ListStack(Container): def __init__(self): self._items = [] def add(self, x): self._items.append(x) def remove(self): return self._items.pop() def __len__(self): return len(self._items) print(ListStack().is_empty()) # True # Container() -> TypeError: can't instantiate abstract class
  • An abstract base class declares the operations every implementation must provide
  • A subclass that forgets one cannot even be created — the mistake is caught early
  • Concrete helpers (is_empty) are written once and shared
This is the ADT idea

Interface = the abstract class. Implementation = each subclass (array-based, linked-list-based…).

Design

Composition vs Inheritance

class BadStack(list): # "a stack IS a list"? def push(self, x): self.append(x) s = BadStack() s.push(1) s.push(2) s.insert(0, 99) # every list method came along... print(s) # [99, 1, 2] <- LIFO is broken class GoodStack: # "a stack HAS a list" def __init__(self): self._items = [] def push(self, x): self._items.append(x) def pop(self): return self._items.pop()
InheritanceComposition
Relationship"is-a""has-a"
ExposesAll parent methodsOnly what you choose
Data structuresRarely rightUsually right

A linked list has nodes. A stack has a list. Prefer composition unless the "is-a" relationship is genuinely true.

References

Variables Are References

a = [1, 2, 3] b = a # b is another NAME for the same list b.append(4) print(a) # [1, 2, 3, 4] print(a is b) # True (same object) c = list(a) # a new list with the same items print(c == a, c is a) # True False import copy grid = [[0, 0], [0, 0]] shallow = copy.copy(grid) deep = copy.deepcopy(grid) grid[0][0] = 9 print(shallow[0][0], deep[0][0]) # 9 0
  • A variable stores a reference (arrow) to an object, not the object itself
  • == compares values; is checks it is the very same object
  • Assignment never copies. A shallow copy copies the outer container only; deepcopy copies everything inside too

Use is None (not == None) when checking for the end of a linked list.

Comparison

Comparing Objects: __eq__ and __lt__

from functools import total_ordering @total_ordering class Task: def __init__(self, priority, name): self.priority = priority self.name = name def __eq__(self, other): return self.priority == other.priority def __lt__(self, other): return self.priority < other.priority def __repr__(self): return f"Task({self.priority}, {self.name!r})" tasks = [Task(3, "email"), Task(1, "exam"), Task(2, "lab")] print(sorted(tasks)) # [Task(1, 'exam'), Task(2, 'lab'), Task(3, 'email')] print(min(tasks).name) # exam
  • sorted, min, max and heaps all need < to be defined
  • @total_ordering fills in <=, >, >= from __eq__ and __lt__
  • Without __lt__: TypeError: '<' not supported

Comparison

Less Boilerplate with @dataclass

from dataclasses import dataclass, field @dataclass(order=True) class Job: priority: int name: str = field(compare=False) jobs = [Job(2, "print"), Job(1, "backup")] print(sorted(jobs)[0]) # Job(priority=1, name='backup') print(Job(1, "a") == Job(1, "b")) # True (name is not compared)
  • @dataclass writes __init__, __repr__ and __eq__ for you
  • order=True adds <, >… comparing fields in order
  • field(compare=False) leaves a field out of comparisons

Great for records stored inside a structure (jobs, edges, entries). Write the structure itself as a normal class.

Robustness

Exceptions in Data Structures

class EmptyQueueError(Exception): """Raised when removing from an empty queue.""" class Queue: def __init__(self): self._items = [] def enqueue(self, x): self._items.append(x) def dequeue(self): if not self._items: raise EmptyQueueError("dequeue from empty queue") return self._items.pop(0) q = Queue() try: q.dequeue() except EmptyQueueError as e: print("Handled:", e) # Handled: dequeue from empty queue
  • Fail loudly with a clear message instead of returning a confusing None
  • Use built-ins when they fit: IndexError (position), KeyError (missing key), ValueError (bad argument)
  • A custom exception class makes the error easy to catch specifically
Precondition

Document what must be true before a call: "dequeue requires a non-empty queue".

Readability

Type Hints and Generic Containers

from typing import Generic, Optional, TypeVar T = TypeVar("T") class Box(Generic[T]): def __init__(self, item: T) -> None: self.item = item def get(self) -> T: return self.item def find(xs: list[int], target: int) -> Optional[int]: for i, x in enumerate(xs): if x == target: return i return None print(Box(42).get(), find([4, 8, 15], 8)) # 42 1
  • Hints document intent: -> Optional[int] says "an index, or None"
  • Python does not enforce them at runtime; tools like mypy and your editor do
  • Generic[T] lets one Stack[T] class describe a stack of ints, of strings, of nodes…
Course rule

Type hints are optional in assignments but recommended in project work.

Pitfalls

Common Mistakes

Missing self

def push(x) → TypeError: takes 1 positional argument but 2 were given. Instance methods need self first.

Shared mutable state

A list as a class attribute or default argument is shared by every object. Create it in __init__.

is vs ==

is checks identity. Use == for values and is None for "no node".

Forgetting super().__init__

The parent's attributes are never created → AttributeError later, far from the real bug.

Leaking the representation

Returning self._items lets callers modify your internals. Return a copy, or only single items.

Changing a list while looping over it

Removing items inside for x in items skips elements. Loop over a copy or build a new list.

Key Takeaways

  • A class is a blueprint; objects are its instances, each with its own attributes
  • self is the object a method acts on; __init__ sets up its attributes
  • Put mutable data in __init__ — class attributes are shared
  • Encapsulate the representation; expose only the ADT operations
  • Dunder methods (__len__, __iter__, __lt__…) make structures feel built-in
  • Inheritance = "is-a"; composition = "has-a". Data structures usually want composition
  • Abstract base classes express an ADT interface in code
  • Variables hold references; assignment never copies
  • Linked structures are objects whose attributes point to other objects
  • Raise clear exceptions for invalid operations like popping an empty stack
